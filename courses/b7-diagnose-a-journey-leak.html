Part 1 · the drill-down from money to screen

The extended diagnosis workflow 11 min live

The metrics course taught steps 1-2: confirm the drop is real, then let the driver tree name the lever. This course adds four more layers underneath the conversion lever. Six steps, each one narrowing the search space, each one using an instrument you have already built in this track.

Confirm it is real. Tracking outage? Seasonality? Check event volumes and the same week last year before anyone panics. A fake drop diagnosed as real wastes a week.

Tree: which lever. GMV = sessions x CR x AOV. The prequel's driver tree already ran: sessions held, AOV held, CR fell. Done - inherited from the metrics course.

Gates: which of the four fell. CR is a product of PDP penetration x add-to-cart x checkout start x completion. Pull the four gate rates WoW and find the one that moved.

Doors + paths: mix or quality. A gate is an average across five doors and two paths. Use b2's decomposition: did the door MIX shift, or did one door's QUALITY fall?

Screen / step: where exactly. Drill into the screen-level instruments - b5's engagement events on the PDP, b6's step completions in checkout - until you can name one screen or one step.

Write the screen-level finding. One paragraph: the drop, the lever, the gate, the door, the screen, the suspected cause, the owner, the action, the re-check date. Demo 2 gives you the template.

LiveWhy the extra layers exist at all4 min▶

The prequel could say "CR fell" - and then it had to stop, because CR is a blend of four gates, five doors, two paths, and a dozen screens. Everything you built in b1-b6 exists for exactly this Monday:

  • The gates (b4's machine) split CR into four owned rates - the first cut.
  • The doors (b2's decomposition) split each gate into mix versus quality - the second cut.
  • The screen instruments (b5's engagement events, b6's checkout steps) point at pixels - the final cut.

Without the layers, "CR fell 9%" becomes a room full of teams each explaining why it is not them. With the layers, it becomes one team's Tuesday ticket.

Run the diagnosis live ★ 15 min · everyone works

Here is b4's machine again, loaded with three competing hypotheses instead of four fixes. Each lever recreates this week's reported drop through a different gate. Your job: prove the top line cannot tell them apart, then break the tie with gate-level data.

{
  "sessions": 360000, "aov": 68,
  "stages": [
    { "label": "Sessions" },
    { "label": "PDP sessions",      "rate": 0.40, "rateLabel": "PDP penetration" },
    { "label": "Cart sessions",     "rate": 0.25, "rateLabel": "add-to-cart" },
    { "label": "Checkout sessions", "rate": 0.45, "rateLabel": "checkout start" },
    { "label": "Orders",            "rate": 0.60, "rateLabel": "completion" }
  ],
  "levers": [
    { "stage": 1, "to": 0.364, "label": "This week: PDP penetration fell", "desc": "40% down to 36.4% - the reported drop, recreated" },
    { "stage": 2, "to": 0.2275, "label": "Alt hypothesis: add-to-cart fell", "desc": "25% down to 22.75% - produces the same -9%" },
    { "stage": 4, "to": 0.546, "label": "Alt hypothesis: completion fell", "desc": "60% down to 54.6% - also the same -9%" }
  ]
}

Toggle each hypothesis alone. All three land on roughly the same orders line, about 9% below baseline. No coincidence: 0.364/0.40 = 0.2275/0.25 = 0.546/0.60 = 0.91, and in a multiplicative flow a 0.91x on ANY single gate passes straight through as a 0.91x on orders. The top line literally cannot tell them apart - that is WHY the journey layers exist.

Break the tie with gate-level counts. Now pull the stage counts, not the ratios of ratios. This week PDP sessions fell to about 131,000 (360,000 x 36.4%), while cart-rate-of-PDP and both checkout gates held at 25% / 45% / 60%. Hypothesis 1 wins: the leak is above the PDP, in getting people TO products.

Drill into the doors with b2's table. Door mix held - same five shares as always. But Home's reach-PDP quality fell from 20% to 16% after a homepage banner takeover buried the catalog modules; every other door held its rate. The leak has an address: the homepage.

Real world

This ambiguity is the most common diagnosis failure in the wild. A war room stares at "CR down 9%" and three teams each run their own analysis proving it is someone else's gate. Gate-level session counts settle it in one query - which is why b8's scorecard tracks the four gate COUNTS weekly, not just the blended CR.

Write the screen-level finding ★ 10 min · everyone writes

A diagnosis that lives in a dashboard dies in a dashboard. The deliverable is one paragraph, in a fixed shape, that any executive can read in twenty seconds and any team can act on. Memorize the template; fill it every time.

LiveThe template, then the filled version6 min▶

The template: "GMV fell [X]% WoW. Tree: CR lever. Gate: [gate] fell [from] to [to]. Doors: [mix or quality, which door]. Screen: [the address]. Suspected cause: [change/incident]. Owner: [team]. Action: [fix]. Re-check: [date]."

If your last sentence names a number instead of a screen and a team, you stopped one layer too early - go back to step 5.
Self-studyThe false-positive checklist - before you accuse a screen4 min read▶

Three impostors produce exactly this signature without any real behavior change. Run this checklist between step 1 and step 6, every time:

  • Instrumentation outage. A screen stopped firing its events - b1's trap. A silent view_item makes PDP penetration "fall" while shoppers browse happily. Check raw event volumes per screen BEFORE any business panic; a screen at near-zero events is a bug report, not a leak.
  • App release the same day. A new version can change what fires and when. Split every gate by app version: if the drop lives entirely in the new build, suspect the build - either its tracking or a genuinely broken screen it shipped.
  • Campaign mix. A paid flood through a weak door (say, a burst of Other-door retargeting) drags the blended gate down while every door's own quality holds. That is a mix effect, not a quality leak - b2's decomposition separates them in one table.
Homework

Try it yourself - this week ◐ 25-35 min total

  • Find your worst week this quarter - the biggest WoW drop in orders or GMV you can locate.
  • Run all six steps on it for real: confirm real, tree, gates, doors and paths, screen or step, finding.
  • Run the false-positive checklist before writing anything: event volumes, releases that week, campaign mix.
  • Write the finding in the template - even if it honestly ends "seasonal gravity, no action". A clean no-action finding is still a finding, and it saves the next analyst the same week of work.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Three different gate drops all produced the same -9% orders in the simulator. Why?

0.364/0.40 = 0.2275/0.25 = 0.546/0.60 = 0.91. The top line carries the product of the gates, so it cannot say which factor moved - that ambiguity is the whole reason the journey layers exist.

2 · What data breaks the tie between the three hypotheses?

The blended CR is ambiguous; the per-stage counts are not. One query showing PDP sessions down and cart/checkout/completion rates flat localizes the leak above the PDP immediately.

3 · Which of these is a COMPLETE journey finding?

A finding ends with a screen and an owner, not a metric. Option A stops at step 3 of 6; the template forces you all the way down to the homepage, merchandising, and Friday's re-check.
